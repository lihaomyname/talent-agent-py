# 多模态职位需求与候选人匹配方案 Review

评审日期：2026-09-17
评审对象：`openspec/changes/add-multimodal-evidence-matching/`
评审结论：整体可行；按照本报告中的用户确认意见修订提案后实施。

本文记录方案评审与用户决策，不表示功能已经实现。此次仅新增 review 报告，未修改应用代码、数据库或原 OpenSpec 工件。原提案已通过 OpenSpec 严格格式校验；图片模型能力、招聘接口数据完整性及实际性能仍需验证。

## 一、已确认的决策

| 事项 | 用户确认后的要求 |
| --- | --- |
| 搜索返回数据 | 增加经历信息，为后续模型匹配提供资料；保持现有列表卡片兼容。 |
| 确认卡片 | 支持查看、增加、修改、删除搜索条件、必须核验项和偏好；多轮对话也支持修改。 |
| 任务打断 | 新旧流程共用会话任务控制，避免两套独立运行机制。 |
| 数据保留 | 不采用纯内存方案；需求、匹配任务、结果及继续检索所需记录保存数据库。 |
| 搜索预算和停止规则 | 以新提案为准，保留默认 5 批、50 人、120 秒等预算，以及有偏好时继续择优的规则。 |

用户已明确采用新提案的停止规则。本轮评审中“默认找到 10 人就停止，再提供深入匹配选项”的建议不采纳；更早讨论的默认 10 页也不作为本期默认值。

## 二、认可并保留的整体方案

1. 自然语言与职位截图统一形成 `SearchRequirements`。非职位图片、不清晰图片或重要歧义明确提示，不凭空构造职位需求。
2. 截图直接生成结构化需求；自然语言摘要用于用户理解，不将摘要再次交给原 Agent 解析。
3. 将可执行搜索条件、必须核验项、偏好分开。简单搜索沿用原逻辑，含经历核验或偏好的需求进入匹配流程。
4. 复用实体解析、查询编译和招聘接口适配，避免每一页重复执行原 Graph 的解析、澄清和最终结果写入。
5. 模型负责需求理解与证据判断，程序负责分页、预算、去重和停止。这是有边界的 Agent 工作流，不要求模型自由选择任意工具。
6. 采用 SUPPORTED、PARTIAL、UNKNOWN、CONTRADICTED 证据状态；信息不足不等于不具备能力，偏好不满足不直接淘汰。
7. 只说明已检查范围内的推荐结果，不声称全库最优，不编造综合匹配分数，不自动放宽用户要求。

## 三、需要落实的调整

### R1：搜索返回增加经历信息

现有 `TalentSearchResponse` 仅包含候选人卡片、总数与分页信息，`JavaTalentClient._candidate_card()` 未保留教育和工作经历。因此，本项本质上就是扩展内部检索返回信息，使匹配节点能取得经历。

建议定义清晰的匹配检索返回类型，包含展示卡片、`CandidateProfile` 和分页信息。底层 HTTP 请求及分页解析共用；原 V1 卡片和接口输出保持兼容。不要把整个招聘宽响应无差别传给模型或前端。

经历至少保留职位、公司、起止日期、工作描述、教育信息及证据来源。缺失、截断和日期语义不明需要显式标记。列表是否提供足够信息必须用授权脱敏样本验证，不默认已有完整简历，也不默认需要新增详情接口。

验收：同一页结果可同时生成原有卡片和匹配资料；经历缺失时仍能正常展示卡片，并将相关核验项标为信息不足。

### R2：确认卡片与多轮修改覆盖全部需求

确认卡片至少分为搜索条件、必须核验项、偏好、待澄清或面试待验证项。支持编辑内容、增加、删除及调整分类；明确提示哪些项决定入选、哪些仅影响排序。系统不得静默降低明确的硬要求。

例如：本科是搜索条件；一年以上射击战斗策划经验是专项经历核验；枪械调优需要具体证据；沟通及抗压能力建议由用户确认列为面试待验证项；编辑器创作经验优先属于偏好。专项经验年限不得偷换为总工龄，招聘地点不得自动变成候选人现居地。

对话中的“把学历改成硕士”“去掉编辑器经验偏好”“将射击经历改为必须满足”都应生成明确的需求变更。未提及的内容保留，删除必须可明确表达，不能用缺失字段表示删除。

任何影响检索或匹配的修改生成新需求版本，旧版本和旧结果作为历史保留，旧游标不可用于新版本。初期按新版本重新检索与评估，避免引入跨版本缓存复用复杂度。运行期间编辑后确认提交新版本，才替代旧任务；仅打开编辑卡片不应取消任务。

验收：页面编辑与对话修改具有一致结果；仅修改偏好也能生效；原结果保留且可看出对应需求版本。

### R3：共用现有会话任务控制

现有 `TaskRegistry` 已提供取消、替换和活动任务判断。普通找人与职位匹配应共用该机制；匹配服务管理自己的业务上下文，不另建互不知情的活动任务体系。

意图判断先决定是否需要替代当前工作。闲聊不打断；查询进度返回当前状态；停止取消任务；新搜索或确认后的需求变更替代旧任务。停止后不启动新的模型或招聘请求，旧结果不得覆盖当前需求。

采用尽力取消，不要求撤销已经完成的外部调用或数据库写入。已落库记录作为历史保留，最后通过任务状态与需求版本区分是否仍有效，不增加分布式调度或复杂补偿机制。

验收：普通搜索和职位匹配相互切换时，旧任务停止推进；“你好”等闲聊不取消任务；历史记录不会因替代而丢失。

### R4：改为数据库持久化

这是对原提案的明确变更：取消“不改数据库、不加迁移、只在内存保存、重启即丢失匹配历史”的约束。复用项目现有 MySQL、SQLAlchemy 和 Alembic，不引入另一套存储框架。记录保留属于业务历史和任务恢复，不等于引入长期记忆或向量检索。

建议按以下逻辑数据组织，具体表拆分在设计修订时确定，优先保持简单：

| 数据 | 需要保存的内容 |
| --- | --- |
| 需求版本 | 所属用户和会话、输入类型、提取文本、结构化搜索条件、核验项、偏好、用户确认内容和版本。 |
| 匹配运行 | 对应需求版本、运行状态、预算快照及消耗、进度、停止原因、错误摘要和时间。 |
| 检索进度与候选评估 | 固定查询、下一页或批内位置、已检查候选人、评估状态、必要资料快照、证据、未处理缓冲及未展示候选池。 |
| 结果分组 | 每次首次匹配或“继续找”的展示顺序、已展示候选人及其结论，用于历史回显和排除重复。 |

主键、归属、状态、版本等常用检索字段用明确列；变动较多的需求和证据可采用类型化模型对应的 JSON 快照。表、列、状态枚举必须有中文注释；不要只在 Python 中加注释而遗漏数据库定义。

每批处理完成后提交评估记录和游标，保证游标不会越过尚未保存的候选人。部分批次未处理完时保存缓冲或明确批内位置；停止、超时和失败时保存已完成进度。事务只包数据库更新，不跨越模型或 HTTP 等待。业务记录和任务状态落库，`asyncio.Task` 等运行时对象仍在内存。

刷新、关闭页面后重新进入、服务重启后均从数据库恢复历史，而不是只依赖 sessionStorage。建议服务重启后将未完成运行标记为中断，展示已有结果，由用户主动继续；不要求后台自动恢复正在进行的模型调用。继续时重新获得当前请求身份和 Cookie，从已提交进度恢复，未提交的一小段工作允许重新执行并去重。

沿用新提案“每次继续重置本轮预算”的规则，同时保留历次运行预算与消耗，不把多轮运行统计混为一轮。

不持久化 Cookie、模型密钥；无需因保存历史而保存原始截图或完整招聘响应。保存必要的提取文本及证据快照即可。历史候选资料展示和继续检索都需校验当前权限，数据库中存在记录不代表当前仍有招聘数据访问权。数据清理规则后续明确，不能继续沿用 30 分钟内存 TTL 删除业务历史。

验收：重启后仍能看到需求、修改记录、结果和停止原因；继续不重复展示已展示人选、不跳过未处理人选；取消或失败保留已完成结果；原 V1 历史行为不受影响。

### R5：严格沿用新提案的预算与停止语义

| 配置 | 初始值 |
| --- | --- |
| 每组目标结果 | 10 人 |
| 招聘接口每页 | 10 人 |
| 每轮最多搜索调用 | 5 次 |
| 每轮最多检查不同候选人 | 50 人 |
| 模型每批候选人 | 最多 5 人 |
| 每轮匹配模型尝试 | 最多 20 次，包含修复 |
| 每轮总运行时间 | 120 秒 |

以上参数可配置，属于待真实评测调整的初始值，不是已验证性能承诺。需求提取使用独立超时和一次结构修复上限。

- 无偏好：已有 10 人满足必须条件时提前结束。
- 有偏好：默认检查至预算或数据结束后择优；已有 10 人满足全部偏好时可以提前结束。
- 达到任一预算、数据耗尽、零新增、用户停止、需求替代或依赖错误时，按原提案停止原因处理。人数不足如实展示，不降低硬门槛。
- “继续找 10 位”：同一需求版本，先使用已评估未展示池，再继续读取未消费位置，重置本轮预算并排除已展示者。
- 内部分页更新进度，不每页创建聊天结果；首次匹配和每次用户继续分别生成一组最终汇总。

## 四、实施前仍需验证的事项

1. 实际网关的 `deepseek-flash` 图片输入与结构化输出能力，用合成职位图片验证，不能凭模型名认定支持。
2. 列表经历字段完整度、日期与 `workYears` 语义、分页终止信息。资料不足输出 UNKNOWN，不补写经历。
3. 当前权限如何覆盖历史候选结果读取及缓存复用；若没有独立授权校验能力，需要经过授权查询重新确认再展示候选资料。
4. 5 批、50 人、120 秒条件下的真实完成率和延迟，尤其是存在多个偏好时；限制达到后明确说明已检查范围。
5. 证据引用校验只能证明引用存在，不能自动证明模型结论正确。用合成评测验证“搜打撤经历不直接证明枪械调优”“任职时长不等于技能时长”等判断。
