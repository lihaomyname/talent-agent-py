项目概述

Talent Agent：自然语言找人编排服务

该项目面向招聘人员，将日常使用的找人表达转换为招聘系统能够执行的结构化查询。招聘人员不需要理解接口字段，也不需要逐项填写复杂表单，只需描述职位、学历、年限、公司、学校和城市等条件，系统负责解析、澄清、校验并完成搜索。

项目并不是让大模型直接决定“应该推荐谁”。大模型只负责理解语言和提取结构，Python 服务负责执行边界、状态流转和确定性校验，Java 招聘系统继续负责业务编码、用户权限以及候选人召回。这样既保留了自然语言交互的便利，也避免模型绕过原有招聘规则。

在原有固定条件搜索之外，系统增加了可选的偏好匹配能力。例如“最好有支付系统经验”不会被强行编译成招聘接口不支持的过滤条件，而是在固定条件召回后，读取候选人的教育与工作经历，寻找有明确证据支持的候选人。没有偏好时，系统仍按原流程返回一页十人，由用户自行翻页。

九类可执行搜索条件结构化澄清版本化搜索计划固定 LangGraph 编排普通分页与偏好匹配双分支图文统一消息入口
Part 01

项目介绍与搜索能力

系统解决的不是“让大模型自由检索简历”，而是让招聘人员用日常表达完成一套受控搜索。模型负责理解，Python 负责校验与编排，Java 招聘系统负责实体编码、权限和最终召回。

自然语言输入

例如“找 5 年以上 Java 后端，现居杭州，本科，在网易工作过”。系统将其转换为结构化 SearchPlan。

结构化澄清

遇到“杭州”这类范围不清的表达，不猜测语义，而是给出“现居住地 / 期望工作地”按钮。

受控执行

固定条件交给 Java 招聘接口。Python 不直连人才库，不自行拼装 Elasticsearch 查询，也不绕过现有权限。

项目为什么采用这种设计

自然语言负责降低使用门槛

招聘人员的表达通常混合职位、地域、履历和主观偏好。如果直接要求用户填写十几个筛选框，效率并不高；自然语言入口先接住完整意图，再把可执行部分收敛为固定字段。

封闭计划负责控制执行风险

模型输出必须通过 Pydantic 类型和 Python 规则校验。模型不能生成任意 SQL、不能直接调用 Elasticsearch，也不能自行编造城市、学校、公司和学历的业务编码。

澄清优先于猜测

“杭州”可能指现居住地，也可能指期望工作地；“网易”可能指当前公司，也可能指历史经历。系统把这种歧义转换成有限选项，让用户做一次明确选择。

偏好和硬条件分离

学历、年限、城市等条件可由招聘接口稳定执行；支付、电商、特定项目经验等信息只能从经历文本中判断。两者采用不同执行路径，避免把“简历没写”错误理解为“不满足”。

支持的九类封闭式搜索

搜索字段示例关键语义
候选人姓名“找张三”默认精确匹配
候选人职位“做过 Java 后端的人”可限定当前职位或当前及历史职位
最低学历“本科及以上”学历名称由 Java 解析为业务编码
工作年限“5 年以上”“3 到 5 年”支持上限、下限和区间
公司经历“在网易工作过”区分当前公司与历史任职公司
毕业院校“浙江大学毕业”学校名称由招聘系统解析
期望工作地“期望去上海”对应求职意向，不等同于现居地
现居住地“现在住在杭州”对应候选人当前城市
院校标签“第一学历 985”支持 985、211 等标签及第一学历限制
所谓“封闭式”，不是交互僵硬。 它指可执行字段是明确的白名单。用户仍然可以自由表达，但最终进入招聘接口的只能是已经定义、已经校验的条件。

期望搜索：普通条件与偏好分开处理

没有偏好：走原搜索

  1. 解析九类固定条件
  2. 必要时用卡片澄清
  3. 调用招聘系统返回 10 人
  4. 用户通过上一页、下一页继续浏览

存在偏好：增加证据匹配

  1. 固定条件仍用于招聘系统召回
  2. 模型只阅读教育和工作经历
  3. 支持或部分支持的候选人进入推荐
  4. 不足 10 人时继续向后翻页，直到命中目标或达到阈值

偏好示例：“最好有支付系统经验”“电商业务背景优先”。候选资料没有写某项能力时记为“信息不足”，不会被描述成“不具备”；但信息不足的人不会占用偏好推荐名额。

一个完整例子

用户输入：“找 5 年以上 Java 后端，杭州，本科，最好有支付系统经验。”

第一步，澄清：“杭州”范围不明确，页面给出“现居住地”和“期望工作地”两个按钮。

第二步，固定召回：用户选择后，职位、工作年限、学历和城市被编译为招聘接口参数，每页读取 10 位候选人。

第三步，偏好判断：模型只查看这 10 位候选人的教育和工作经历，判断支付系统经验是“支持、部分支持或信息不足”。

第四步，继续搜索：只保留支持或部分支持的人；如果不足 10 人，继续读取下一页，直到满足人数、候选池耗尽或达到运行阈值。

最终展示：候选人仍使用统一列表卡片，额外显示“支付系统经验”等标签；展开后可查看推荐理由、证据状态、教育经历和工作经历。

技术栈、数据库与表结构

整体采用端口与适配器思路：领域模型不依赖具体模型厂商和招聘接口，外部依赖都收敛在客户端层；数据库只保存 Agent 自己的会话与执行状态。

Python Agent 服务

负责消息路由、计划生成、确定性校验、LangGraph 编排、运行取消、分页引用和偏好证据评估。

Java 招聘系统

五张主表

agent_sessions
会话主表。保存用户归属、当前计划版本和活动 Run 指针；它是会话当前状态的入口。
agent_messages
消息流水。通过 session_id + client_message_id 保证幂等，通过 sequence 保证会话内顺序；outcome_json 保存可恢复的回复快照。
agent_runs
执行记录。记录排队、运行、澄清、成功、失败、取消和被替代状态；result_json 保存搜索或偏好匹配快照。
agent_search_plans
不可变计划版本。每次条件变更生成新版本，plan_json 保存完整 SearchPlan，便于多轮记忆和审计。
agent_pending_clarifications
待澄清状态。每个会话最多一条，保存澄清卡和暂停时的草稿；回答后继续原 Run 逻辑。

核心建表语句（MySQL 表达）

CREATE TABLE agent_sessions (
  id VARCHAR(64) PRIMARY KEY,
  owner_user_id VARCHAR(128) NOT NULL,
  active_run_id VARCHAR(64),
  current_plan_version INT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  INDEX ix_sessions_owner (owner_user_id)
);

CREATE TABLE agent_messages (
  id VARCHAR(64) PRIMARY KEY,
  session_id VARCHAR(64) NOT NULL,
  client_message_id VARCHAR(128) NOT NULL,
  sequence BIGINT NOT NULL,
  role VARCHAR(20) NOT NULL,
  content TEXT NOT NULL,
  outcome_json JSON,
  route_type VARCHAR(40),
  created_at DATETIME NOT NULL,
  UNIQUE KEY uq_message_client_id (session_id, client_message_id),
  UNIQUE KEY uq_message_sequence (session_id, sequence),
  FOREIGN KEY (session_id) REFERENCES agent_sessions(id) ON DELETE CASCADE
);

CREATE TABLE agent_runs (
  id VARCHAR(64) PRIMARY KEY,
  session_id VARCHAR(64) NOT NULL,
  trigger_message_sequence BIGINT,
  status VARCHAR(40) NOT NULL,
  stage VARCHAR(100) NOT NULL,
  result_status VARCHAR(40),
  error_code VARCHAR(100),
  result_json JSON,
  superseded_by_run_id VARCHAR(64),
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  FOREIGN KEY (session_id) REFERENCES agent_sessions(id) ON DELETE CASCADE
);
CREATE TABLE agent_search_plans (
  id VARCHAR(64) PRIMARY KEY,
  session_id VARCHAR(64) NOT NULL,
  version INT NOT NULL,
  applied_through_message_seq BIGINT NOT NULL,
  plan_json JSON NOT NULL,
  created_at DATETIME NOT NULL,
  UNIQUE KEY uq_plan_version (session_id, version),
  FOREIGN KEY (session_id)
    REFERENCES agent_sessions(id) ON DELETE CASCADE
);
CREATE TABLE agent_pending_clarifications (
  question_id VARCHAR(64) PRIMARY KEY,
  session_id VARCHAR(64) NOT NULL UNIQUE,
  source_message_sequence BIGINT NOT NULL,
  card_json JSON NOT NULL,
  draft_json JSON,
  created_at DATETIME NOT NULL,
  FOREIGN KEY (session_id)
    REFERENCES agent_sessions(id) ON DELETE CASCADE
);

演示时可用的查询语句

-- 查看某个会话的消息与路由顺序
SELECT sequence, role, route_type, content, created_at
FROM agent_messages
WHERE session_id = :session_id
ORDER BY sequence;

-- 查看计划如何随对话演进
SELECT version, applied_through_message_seq, plan_json, created_at
FROM agent_search_plans
WHERE session_id = :session_id
ORDER BY version;

-- 查看一次运行停在哪个阶段
SELECT status, stage, result_status, error_code, updated_at
FROM agent_runs
WHERE id = :run_id;
数据边界：Python 不保存招聘登录 Cookie，不直连人才库。Cookie 只在当前请求协程内透传给白名单 Java 地址。候选详情只以受控快照形式存在 Run JSON 中，日志会脱敏手机号、邮箱、证件号和密钥。

表之间如何配合

一个会话对应一条 agent_sessions 记录，并通过 active_run_id 和 current_plan_version 指向当前状态。每次用户输入先进入 agent_messages；需要执行搜索时创建 agent_runs。搜索条件确认后生成新的 agent_search_plans 版本；遇到歧义时，将澄清卡和未完成草稿放入 agent_pending_clarifications。用户回答后删除待澄清记录，并继续原来的计划。

计划采用不可变版本，而不是原地覆盖。这样可以明确知道一次 Run 使用的是哪个版本，也可以防止旧的分页引用或旧任务覆盖最新搜索结果。消息的 outcome_json 与运行的 result_json 用于刷新页面后的恢复。

各节点的职责

节点读取内容输出或作用
load_context当前计划和尚未被计划吸收的消息恢复本轮所需的最小上下文
parse_plan消息、现有计划和路由类型首次生成 SearchPlanDraft，修改时生成 PlanPatch
validate结构化草稿检查字段范围、冲突、不支持条件和歧义
resolve_entities城市、公司、学校和学历名称通过 Java 获取权威业务编码，再次校验
clarify第一个阻塞项及当前草稿保存澄清卡，Run 进入待澄清状态并正常结束请求
save_plan已通过校验的草稿写入不可变计划版本，并更新会话当前版本
compile_searchSearchPlan确定性编译为 Java 搜索请求，不再调用模型
search_candidates搜索请求和可信用户上下文调用招聘接口，取得权限范围内候选人
finalize候选人结果、Run 和计划版本保存安全结果快照，生成下一页引用并结束运行

模型不能直接搜人

模型只生成 Pydantic 可校验的 Draft 或 Patch。工具、节点和边全部由代码固定。

每一步都能恢复

消息、Plan、Run、澄清卡和结果页都落在数据库。刷新页面后按快照恢复，而不是依赖浏览器内存。

新需求可替代旧运行

修改搜索时，新 Run 会替代旧 Run；闲聊、进度查询和翻页不会无故创建另一套计划。
